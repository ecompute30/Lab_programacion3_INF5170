¿Qué es el patrón MVC?

Modelo-Vista-Controlador es un patrón de arquitectura de software que separa una aplicación en tres responsabilidades independientes: los datos, lo que el usuario ve y la lógica que conecta ambos.

Su objetivo es que un cambio en una capa (por ejemplo, rediseñar la interfaz) no obligue a tocar las otras (la lógica de negocio o los datos).

Origen del modelo MVC

  • Creado por Trygve Reenskaug en 1979, durante su estadía en Xerox PARC.
  • Diseñado originalmente para Smalltalk-80, uno de los primeros lenguajes orientados a objetos con interfaz gráfica.
  • El problema que resolvía: las aplicaciones gráficas mezclaban datos, lógica y pantalla en el mismo código, haciéndolas difíciles de mantener.
  • MVC nació para que distintos desarrolladores pudieran trabajar la interfaz y la lógica por separado, sin pisarse.

Los tres componentes

📦 Modelo

Representa los datos y las reglas de negocio. No sabe nada de cómo se muestran.

🖥️ Vista

Lo que el usuario ve e interactúa. Muestra datos del Modelo, sin lógica de negocio propia.

🎮 Controlador

Recibe la entrada del usuario, decide qué hacer con el Modelo y qué Vista mostrar.

El flujo típico: Usuario → Controlador → Modelo → Controlador → Vista → Usuario.

Ventajas y desventajas

VentajasDesventajas
Separación de responsabilidades claraCurva de aprendizaje para principiantes
Facilita pruebas unitarias (Modelo aislado de la UI)Puede ser excesivo para apps muy pequeñas
Permite trabajo paralelo en equipo (front/back)Riesgo de un Controlador "gordo" si no se diseña bien
Reutilización: varias Vistas sobre el mismo ModeloMás archivos/capas que un script simple

¿Por qué sigue siendo importante?

  • Porque la idea (separar datos, presentación y lógica) es independiente de la tecnología — funciona igual en 1979 que en una API REST de 2026.
  • Casi todo framework web moderno es, en el fondo, una variación de MVC (o de su primo, MVVM).
  • Entender MVC permite entender por qué un framework organiza las carpetas como lo hace, en vez de memorizar la estructura sin razonarla.

MVC tradicional vs. hoy

MVC clásico (Smalltalk)

  • Una sola aplicación de escritorio
  • Vista y Controlador muy acoplados a la UI gráfica local

MVC web moderno

  • Controlador = endpoint HTTP (API REST)
  • Vista puede ser HTML server-side o JSON consumido por un frontend SPA (React/Vue)
  • Modelo suele incluir el ORM y la base de datos

Ejemplo: Sistema de registro de estudiantes

Modelo

Representa los datos del estudiante: matrícula, nombre, carrera, correo. Define cómo se guardan y validan.

Vista

Formulario web donde se registran o consultan estudiantes (como el de la Práctica 7, con nuestras tareas).

Controlador

Recibe los datos del formulario, valida la información y decide qué respuesta/Vista enviar de vuelta.

El mismo ejemplo, en código

Así se vería en nuestra propia Práctica 7 (CRUD de tareas), aplicando MVC:


// MODELO — define la forma del dato y el acceso a la BD
interface Tarea { id: number; titulo: string; completada: boolean }
function crearTarea(titulo: string): Tarea { /* INSERT en SQLite */ }

// VISTA — el formulario HTML que el usuario ve y completa
// (public/index.html + app.js en la Práctica 7)

// CONTROLADOR — recibe la petición, valida y decide la respuesta
app.post('/api/tareas', (req, res) => {
  if (!req.body.titulo) return res.status(400).json({ error: '...' });
  const tarea = crearTarea(req.body.titulo);
  res.status(201).json(tarea); // responde con el Modelo actualizado
});

Conclusión personal

Comprender MVC antes de aprender un framework evita que ese framework se sienta como "magia": cuando se sabe que un Controller de Spring o una View de Django son solo nombres distintos para las mismas tres responsabilidades de 1979, aprender un framework nuevo deja de ser memorizar carpetas y pasa a ser reconocer un patrón ya conocido — exactamente lo que hicimos en la Práctica 7 sin llamarlo "MVC" explícitamente.
